# Database design

- **Engine:** PostgreSQL 16 with `pgvector` (similarity search), `pg_trgm` and `pgcrypto`.
- **Schema:** one application schema, `vyg_requirement`, on the company's shared database instance (`sandbox`). Vyoog is single-tenant (D3): no `tenant_id`, no row-level security.
- **Source of truth:** the Flyway migrations in `database/migrations`, named `Vnnn__short_description.sql`. The Maven build packs them into the application jar (`backend/vyoog-domain/pom.xml`), and Flyway applies them at startup (`spring.flyway.locations: classpath:db/migration`). `V001__baseline.sql` is the baseline.
- **Rules:** migrations are forward-only and are never edited once merged; a schema change is a new migration in the same pull request as the code that needs it; every migration must run against a populated database. Hibernate only validates (`ddl-auto: validate`).
- **Search path:** the connection lists both schemas, `currentSchema=vyg_requirement,public`, because the `pgvector` and `pg_trgm` operators are registered unqualified in `public`.
- **Local database:** `database/init/01-schema.sql` creates the schema when the docker-compose Postgres first starts.
- **Seed data, views, functions, procedures:** created by migrations (for example the seeded gap-rule templates and integration connections), not by separate scripts; the `database/seed`, `views`, `functions` and `procedures` folders are for assets that should not be migrations, and are empty today.
- **Foreign-key indexes (VYB-0910):** every foreign key has an index on its referencing columns (a partial `WHERE col IS NOT NULL` index when the column is nullable), except the "who did it" columns that point at `app_user` (`created_by`, `updated_by`, `changed_by`, `granted_by`, `uploaded_by`, `decided_by` and similar), which nothing filters on and whose parent rows are never deleted. The exceptions are listed, with the reason, in `ForeignKeyIndexIT`; that test fails when a migration adds a foreign key that is neither indexed nor on the list. An index on a hot table slows every write, so an exception needs a reason, not a convenience.
- **Retention of bookkeeping tables (VYB-0910):** `idempotency_key` is purged after 7 days and `webhook_delivery` after 90 (`vyoog.retention.*`, product-owner decision), `rate_limit_hit` after 1 hour, by a nightly job at 03:00. `audit_event` has its own retention (`app_config.audit_retention_days`, partition detach). The webhook window is also the replay-protection window: the signed payload has no timestamp, so an old delivery id that has been purged would be accepted again. See `docs/08-architecture/deployment/running-more-than-one-instance.md`.
- **Check constraints that copy a list (VYB-0911):** a `CHECK (col IN (...))` that mirrors another table's allowed values goes stale when that table changes (`saved_view.status` still listed the old requirement statuses for six migrations). `SavedViewIT` compares the saved-view checks with the requirement table's and with `RequirementStatus`; a migration that changes one must change the other.
- **Export (VYB-0911):** `TenantExportService` exports every table in the schema, read from the catalog, except `flyway_schema_history`, `rate_limit_hit`, `scheduler_lock` (not data) and detached `audit_event_archive_*` tables. A table added by a migration is exported without a code change; `TenantExportIT` fails if one is left out without being named in `NOT_EXPORTED`.
